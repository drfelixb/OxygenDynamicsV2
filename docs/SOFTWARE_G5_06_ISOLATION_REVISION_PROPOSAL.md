# SW-G5-06R proposal — identify and contain the startup escape

28 September 2026. The researcher approved **SW-G5-06R-01/02 implementation and up to three synthetic process-tree checks**, then separately approved one corrected reparenting recheck. After that bounded synthetic evidence, the researcher separately approved **one startup-only MATLAB diagnostic**, with no retry, no Run and cleanup inside 90 seconds; its [pre-launch/result record](SOFTWARE_G5_06R_STARTUP_DIAGNOSTIC.md) is separate. Any recorded-movie run remains unapproved. The researcher accepted the [SW-G5-06 pre-Run stop](SOFTWARE_G5_06_EXECUTION.md) and its untested classification. The consumed SW-G5-06 approval cannot be used to relaunch. SW-G5-07, G5 acceptance and release remain separate decisions.

## Observed problem and evidence limit

The prior supervisor created a dedicated session/PGID **54129**, distinct from its own PGID **54127** and the two pre-existing MATLAB groups. During startup it observed a descendant whose PGID differed from 54129 and stopped the original group before `go.json` or the attempt marker existed. The [saved report](../../reference-validation/software-g5-real-id400-worker-20260928/supervisor-result.json) contains the reason but **not the escaped PID, parent, executable, session, process state or timing**. The worker log only shows that input review began. The escaped process's identity, role, fate and cause of detachment are therefore **unknown**. `parfor` occurs later in the master, but the detector never ran here, so it cannot explain this observed startup escape.

The old `signal_group` stops only the original PGID. It does not establish that a process in a different PGID stopped. The old `descendants` scan also loses an escaped process if it reparents between polls. Neither a clean exit of the launcher nor absence of a later MATLAB process proves that every process from the launch was contained. The revision must not convert this uncertainty into a pass.

## SW-G5-06R-01 — bounded instrumentation and process identity

**User benefit:** a failed pre-Run guard will show *which* process escaped and whether it could continue the analysis. **Owner:** Codex; assistant self-review unless a separate reviewer participates. **Scope:** a new diagnostic supervisor/packet, leaving the original one-use worker, control, report and source untouched. Do not modify scientific code, settings, detector or measurement rules.

Before launch, save a timestamped baseline process snapshot. During startup, retain a rolling series of process-table snapshots at the fastest reliable rate up to a target of roughly 250 ms; record actual sample intervals rather than claiming continuous observation. For every newly observed descendant and every member of the launch PGID, persist monotonic/UTC observation time, PID, PPID, PGID, UID, state, RSS and command/executable. Query its session ID and process start time while it is live. When a PGID mismatch appears, **persist the triggering complete snapshot before sending a signal**, plus the previous snapshot, the ancestor chain, the escaped row's full command line, and the process identity in each subsequent cleanup snapshot. Include the parser's raw `ps` line and any lookup errors. Keep full command lines confined to the local diagnostic packet because they can contain private paths. Verify the host-supported `ps` fields and session lookup before launch; stop if they cannot be read. Save an immutable process-identity registry to follow already observed descendants after reparenting. PID alone or a second-resolution timestamp is not sufficient to authorize a later signal; if a sufficiently precise identity check is unavailable, fail closed. The old report is historical evidence and must not be edited to add guessed details.

**Acceptance check:** a synthetic child deliberately entering a new PGID produces a report with its identity, transition, ancestor chain and before/after process rows. A malformed or missing process observation is an explicit diagnostic failure. **Stop condition:** no startup diagnostic if monitoring or durable evidence capture is unavailable.

## SW-G5-06R-02 — bounded stop and proof of quiescence

**User benefit:** a limit-triggered stop cannot leave a known analysis-capable child working. **Owner:** Codex. **Scope:** supervisor lifecycle only. Maintain the original dedicated PGID plus a registry of all observed launch descendants, even if their PPID or PGID changes. Distinguish the actual MATLAB worker PID from its launcher and helper processes using the worker's reported PID and live process identity. Newly detached or unclassified children are treated as **potentially capable of continuing the run**, not waived by command name alone.

On a pre-Run stop, never write the one-use Run release. If Run was already released, mark the supervisory outcome incomplete and begin termination; deleting a release file cannot undo a started run. Freeze the current process evidence, then signal the verified original PGID and each verified escaped descendant. Signal an escaped *group* only when its current members are all attributed to this launch; otherwise signal only the individually verified PID(s), never an unrelated shared group. Recheck precise process identity immediately before each PID signal. Allow at most 10 seconds for graceful exit, then use force termination for verified survivors. Rescan for up to another 10 seconds and require two consecutive snapshots, at least one second apart, with **no live tracked process** and no newly attributable descendant. Record signal target, identity verification, result and any survivor. A zombie is recorded but is not counted as execution-capable. Failure to verify a PID safely, a lost/reparented untracked process, an escaped process that cannot be stopped, or an ambiguous process role is a **containment failure**. Do not release Run after such a failure and do not claim a clean stop after Run.

The main MATLAB worker must be confirmed dead before calling the run stopped. Because a process-table sampler can miss a child that detaches and exits between samples, **two clean snapshots are evidence of quiescence, not an absolute containment guarantee**. The real-run gate requires evidence that every *observed* process capable of continuing analysis is either inside the stoppable group or independently tracked and stoppable, plus an explicit decision on the remaining observation gap. If startup or synthetic checks cannot establish even that bounded assurance, stop here. A stronger OS-level containment design would need its own platform/approval decision; this proposal does not silently substitute one.

**Acceptance checks:** disposable synthetic trees cover an ordinary child, a child entering a new PGID, and a child reparented after its original parent exits. Each must preserve a separate unrelated process. Each stop report must show zero live tracked processes or explicitly fail. No detector, statistics or recording input is used in these synthetic checks. **Stop condition:** any unresolved survivor, identity ambiguity or unintended signal ends this revision as failed/untested for real-run readiness.

## Separate startup-only diagnostic budget — proposed, not yet approved

| Boundary | Proposed maximum |
|---|---|
| MATLAB starts | **One** disposable startup-only launch in a fresh diagnostic packet, with no retry under this budget. |
| Entry point | A dedicated diagnostic `.m` file that contains **no `ui.Run`, master, detector or statistics call**. It may load the saved G2 request, perform the same read-only ID400 source/GUI preflight that reached the prior stop, report its PID, then wait briefly for observation. No `go.json` is created. |
| Source/output | The same named local ID400 source may be *read* for preflight; verify its three hashes first. No run output folder is claimed and no source or existing packet is mutated. |
| Wall/resource limit | **90 seconds total from process launch**, including preflight and observation; **32 MiB maximum diagnostic evidence**. Stop sooner on a detached/unclassified process, monitor/error-log cap, source mismatch, GUI/preflight error, >2 GiB sampled process-tree RSS, or <8 GiB destination free space. Persist the trigger snapshot before cleanup; reserve space for that snapshot and the stop report within the cap. |
| Cleanup | At most 10 seconds graceful plus 10 seconds force/verification, using the SW-G5-06R-02 rules. If cleanup cannot be proved, report a containment failure and stop all further checks. |
| Result | Identify the escaping process from its saved row and lineage, or report `not_reproduced`/`identity_unresolved` honestly. One startup observation cannot prove that later analysis or `parfor` children are contained. |

This **startup-only diagnostic is a separate approval decision** from implementing the instrumented supervisor and from any future real-acquisition run. If deferred, the present report remains an accepted safe stop and real-acquisition integration remains untested. If approved and the startup escape is understood and cleanly stopped, present the captured evidence and a distinct, bounded proposal for any live recorded-movie attempt. **Do not treat a startup diagnostic pass as approval to Run.**
