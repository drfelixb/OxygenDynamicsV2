# SW-G5-06R-06 decision card — durable live release writer

28 September 2026. The researcher approved **this five-case filesystem-only implementation** with one attempt per case and no automatic retry; the [delivery](SOFTWARE_G5_06R_06_DELIVERY.md) records the result. This card did not authorize a MATLAB launch or live Run release. SW-G5-06R-05 proved one-shot behavior for an in-memory claim, including an exception after a simulated side effect. It did not make a real release crash-safe. Owner: Codex; assistant self-review unless another reviewer actually participates. User benefit: a supervised Run release should be bound to one output and nonce, written at most once, and remain consumed/uncertain after any ambiguous writer failure.

**Proposed bounded implementation.** Add a durable claim for one named disposable output identity and a single live release writer, then connect them to the existing guarded controller. Reserve the claim with atomic no-overwrite creation and durable flush **before** any `go.json` write; never reset or delete it to retry. Bind the claim, ready receipt and release payload to the same nonce, output path, source/settings hashes and worker identity. Preserve the ordering `startup scan → assessment` on each startup snapshot, other preflight/resource checks, then a new final `scan → assessment → durable claim → writer`. The writer must create the token atomically with no overwrite, flush it, and return only after verification. A failure after the claim, including after a possible token side effect, is **uncertain and consumed**: stop and retain the evidence and folder; do not issue a second write or automatically retry. Keep process-tree tracking and a verified stop for any still-running worker. The consumed one-use SW-G5-06 supervisor and saved packets stay unchanged.

**Proposed checks and limit.** Before any evaluation, check saved source/code hashes and review the exact claim/token paths, identity fields and proposed payload. Use at most **five named disposable filesystem-only evaluations**, one attempt per case and no retry. Each case gets a new disposable directory; any preexisting artifact is created only inside that case's fixture. The claim, ready receipt and token payload identities comprise nonce, canonical output path, source/settings hashes and worker identity.

| Named case | Required filesystem-only outcome |
|---|---|
| `single_release_then_fresh_second_call` | A matching ready receipt and payload create one durable claim and one token. A second call with a fresh saved snapshot cannot issue another token or overwrite either artifact. |
| `side_effect_then_writer_exception` | A fault after a simulated token-side effect leaves the durable claim consumed/uncertain. A new controller instance reading the same directory cannot retry or overwrite the token; preserve the error and artifacts. |
| `preexisting_claim_only` | Seed a valid claim but no token. The writer rejects release without changing the claim or creating a token, even if a fresh saved snapshot is eligible. |
| `preexisting_token_only` | Seed a token but no claim. The writer rejects release without overwriting the token or issuing a second one; report the inconsistent preexisting state. |
| `payload_identity_mismatch` | With a matching ready receipt and a newly reserved claim, supply a payload with a different nonce while the other identity fields match. The writer compares the payload against **both** claim and ready receipt, rejects it before token creation, and leaves the claim consumed/uncertain. No corrected-payload retry is authorized. |

**Acceptance and stop.** Report pass/fail/untested for all five cases, source/code hashes, claim/token bytes and hashes where present, exact identity comparison, sink invocations and any retained error. Acceptance requires five passes on the same final code hash, no duplicate or overwritten token, no unconsumed claim after an ambiguous side effect, and no **new** token for the three negative cases; the seeded token must remain unchanged. Stop before evaluation on a hash or path mismatch, existing non-fixture packet, or any route to a live process, MATLAB or Run. Stop at the first failed case and label the rest untested; do not repair and rerun within this five-evaluation budget. No child process, MATLAB, detector, statistics or recorded movie may launch. The implementation decision would authorize these file-only checks; it would **not** authorize a live MATLAB startup, `ui.Run`, or recorded-movie attempt.

After the filesystem-only [delivery](SOFTWARE_G5_06R_06_DELIVERY.md), connecting a live caller or attempting a named real acquisition still needs separate approval and its exact source hashes, settings, support, output path, free-space and process-group checks, runtime/memory/output caps, containment stop and no-retry budget. Real release behavior and the real-acquisition G5 gap remain unverified. SW-G5-07, G5 acceptance and release are separate decisions.
